Prototype evaluation -- analysis and interpretation
====================================================================
Companion to prototype_summary.txt (the numbers). This file is the
interpretation; it is maintained BY HAND and is NOT generated by
scripts/eval_prototype.py. If the prototype parameters change, update
the prose below to match the regenerated prototype_summary.txt.


1. What the generator is -- target tier
--------------------------------------------------------------------
The prototype is a STRONG-PASSWORD generator, in line with the thesis
specification ("secure password generation"). It is NOT a cryptographic
key generator.

A password and a cryptographic key sit on two different ladders. The
prototype's output number belongs only on the password ladder:

  password ladder   weak human-chosen ~30 bits
                    strong-password rule-of-thumb >= ~80 bits
                    this generator, 16-char output ~98 bits (= 16 x log2 70)

  (For reference, NOT directly comparable: cryptographic keys use a
   separate ladder with a different threat model -- AES-128 = 128 bits,
   AES-256 = 256 bits -- defended by raw keyspace size, not by a slow
   verifier-side hash + rate-limit.)

The 16-char demo password (~98 bits) sits well into the strong-password
range. It is not "short of 128" in any meaningful sense: 128 bits is on
the key ladder, a different artifact. The 128-bit figure that appears
across the literature has two distinct sources -- AES-128 keyspace
(cryptographic keys) and lambda = 128 beacon-seed scale (Clark &
Hengartner; Landis & Bonneau) -- neither of which is on the password
ladder.

Password entropy is a deployer-set knob: entropy = length x log2(70).
  16 chars -> ~98 bits    (this demo)
  21 chars -> ~129 bits   (illustrative; length is the deployer's knob)
  41 chars -> ~251 bits   (approaches the pipeline budget below)
There is no data-side ceiling at 98 bits. The upstream IKM carries at least
256 bits of min-entropy: the deploy-set worst-month H_inf is 0.975, so
33 bytes x 8 x 0.975 ~= 257 bits >= 256, and HKDF-Extract yields a 256-bit
PRK. The 256-bit budget is sized so the conditioning pipeline is never the
limiting factor; the chosen demo length (16) is what fixes the output at
~98 bits.

Why a password need not reach 128 bits: a password is defended by a slow
verifier-side hash (Argon2 / bcrypt / scrypt) plus rate-limiting, not by
raw brute-force resistance the way a symmetric key is. NIST SP 800-63B
prescribes no minimum bit count for memorized secrets -- it constrains the
verifier, not the secret. A randomly generated ~98-bit password is already
far beyond any practical offline-cracking budget.


2. Assumptions and estimator caveats
--------------------------------------------------------------------
chi-square i.i.d. assumption. The pooled chi-square goodness-of-fit assumes
i.i.d. characters. HKDF-SHA256 output is treated as computationally i.i.d.
under its PRF security assumption (consistent with NIST SP 800-90
conditioning practice; see SP 800-90B for entropy-source estimation and
SP 800-90C for conditioner construction). The thesis Section 4.6 method box should state
this explicitly.

Miller-Madow entropy bias. The observed Shannon entropy sits ~0.02-0.05
bits/char below the theoretical log2(70) = 6.1293 in ALL five groups. This
is the Miller-Madow bias of the plug-in entropy estimator at N = 1600
samples over m = 70 categories: bias ~= (m-1)/(2N ln2) ~= 0.031 bits/char,
which matches the observation. Per 16-char password this is roughly a
0.5-bit shortfall versus the theoretical 98.07. Because the bias is
identical across all five groups, it REINFORCES -- it does not weaken --
the indistinguishability conclusion.


3. Reading the results
--------------------------------------------------------------------
chi-square outcome. With 30 cells tested at alpha = 0.01, the expected
number of type-I errors is 30 x 0.01 = 0.30 (P(>=1) ~= 26%). In the
current run the lone chi-square failure falls on a BASELINE cell, never on
a market cell -- the 18 market cells produced 0 failures. A single failure
on an ideal-uniform baseline is exactly the sampling noise the type-I rate
predicts; it does not indicate a defect. (The exact failing cell and its
p-value are listed in prototype_summary.txt.)

Cross-reference to Exp 4 -- the "E1" point. Upstream, the raw fused IKM
streams have different 29-test battery profiles by fusion size (n=2, n=3,
n=5 fail different numbers of sub-tests). Downstream, after HKDF, all three
market configurations pass the pooled chi-square at rates indistinguishable
from the ideal baselines (market 6/6 each; baselines 5/6 and 6/6, well
within the type-I noise band described above). HKDF-SHA256 flattens the
upstream fusion-size differences -- this is the prototype-level evidence
for the Exp 4 "E1" finding (a cryptographic extractor downstream absorbs
upstream non-uniformity).

Rejection-sampling fallback. The re-Expand fallback in src/prototype.py
(info_base + 4-byte counter) was triggered 0 times on this sample,
consistent with the ~1e-5 per-password theoretical rate. It is dead code
on this run but is required for correctness on the distribution tail.

Reproducibility. A single 32-byte salt (data/processed/prototype/salt.bin)
seeds the entire demo: the market passwords via the Exp 4 fused streams,
and the B1/B2 baselines via the same salt. Re-running runner_prototype.py
then eval_prototype.py reproduces all 3,000 passwords bit-for-bit.


4. Security model -- public source vs secret salt
--------------------------------------------------------------------
The entropy figures above describe the password SPACE. They do not, on
their own, establish secrecy. The market data is a PUBLIC entropy source:
anyone can re-download the same exchange trades, so an attacker who knows
the harvesting parameters (asset, month, aggregation level, witness
offset) can reproduce the fused stream.

The secrecy of a generated password therefore rests on the HKDF salt being
kept secret, NOT on the market data. The market data contributes freshness
and auditable provenance; the secret salt contributes secrecy. An HKDF salt
is conventionally allowed to be public, but for this secret-password use
case it must be kept secret.

Demo-time salt vs production-time salt. The salt persisted in the
repository (data/processed/prototype/salt.bin) is a DEMO-TIME salt: it is
intentionally public, so that anyone with the same fused streams and this
persisted salt can reproduce the 3,000 passwords bit-for-bit and verify the
demo (Section 3). A PRODUCTION-time salt is the opposite -- it must be kept
secret and rotated per deployment / per epoch. The reproducibility-public
demo salt exists for verification only; it must not be carried into a
production setting that needs the password to stay secret.

This is the key distinction from the beacon literature, whose
financial-data randomness is deliberately PUBLIC and verifiable. The thesis
Discussion should make the framing explicit: the claim is not "financial
data is itself key material", but "public market entropy + a standard KDF
+ a secret salt yields strong passwords" (demo runs are reproducible for
verification; production rotates the salt so per-deployment outputs are
unique).


5. Extensions out of scope
--------------------------------------------------------------------
The thesis deliverable is a strong-password generator. Two adjacent uses
of the same harvested entropy are worth recording but are deliberately
out of scope.

Cryptographic key generation. The same pipeline -- a 33-byte IKM block ->
HKDF-Extract -> a 256-bit PRK -- can key AES-128/256 directly, instead of
the PRK being expanded and mapped to a charset password. Quality is not the
obstacle; throughput is. At the measured n=3 harvest rate (~0.98 h per 256
bits of fused stream; see validation_summary) one 33-byte IKM block accrues
in roughly one hour of real time. That is impractical for high-volume key
issuance, but entirely workable for low-throughput, high-value keys minted
rarely -- root CA keys, election keys, HSM seeding -- where a one-hour
harvest is negligible against the key's lifetime. (An earlier review cited
~7.5 min/key; that figure does not reconcile with the measured throughput
and is not used here -- ~1 h/key is the verified number.)

Public randomness beacon. Using financial data as a *public* randomness
beacon is the literature's original application (Clark & Hengartner;
Landis & Bonneau). It is a different threat model from this thesis: a
beacon output is public and verifiable, and the adversary manipulates the
source rather than predicts it. Landis & Bonneau estimate that manipulating
an S&P-100 beacon would cost on the order of billions of dollars, and a
verifiable delay function is needed to deter a last-look attacker. None of
that machinery applies to the secret-password setting here -- which is why
the beacon route is noted but not pursued.

Important caveat -- statistical randomness is NOT beacon unpredictability.
The chi-square and Exp 4 battery tests in this work prove only that a
passive observer cannot detect patterns in the output. Beacon
unpredictability is a different property: it requires that an adversary
with full knowledge of the public source and configuration cannot predict
the next pulse before it is published. This is not delivered by passing
randomness batteries; it requires either source unpredictability (an
adversary cannot recompute the source faster than the publisher) or a
verifiable delay function. Conflating "passes randomness tests" with
"beacon-unpredictable" is a known anti-pattern in the literature -- the
thesis must not equate the two when discussing this extension.
